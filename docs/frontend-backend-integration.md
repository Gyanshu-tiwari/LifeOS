# 🔌 LIFEOS Frontend ↔ Backend Integration Guide

**Status**: Proposed Frontend Interface (v2.0)  
**Target Environment**: REST API (HTTP/2 or HTTP/1.1) + Real-Time WebSocket  
**Frontend Architecture**: React 18 + TypeScript + Vite + Tailwind CSS + Service Abstraction Layer  

---

## 1. Executive Summary for Backend Engineers

The LIFEOS frontend is designed with a strict **Service Abstraction Layer**.
Components do **NOT** make direct `fetch()` calls or hold hardcoded mock data. All network communication passes through:

```text
React Components / Pages
        ↓
    useLifeOS() Context Hook
        ↓
  Service Modules (`src/api/services/*.ts`)
        ↓
   ApiClient (`src/api/client.ts`)
        ↓
 Backend Endpoints (REST & WebSocket)
```

To switch the entire frontend from local development mock mode to your live backend, simply set the environment variables in `.env`:

```bash
# Set to 'real' to disable mock fallback and query your server
VITE_API_MODE=real

# Base REST API Gateway URL
VITE_API_URL=http://localhost:8000/api/v1

# Real-Time Agent Stream WebSocket URL
VITE_WS_URL=ws://localhost:8000/ws/agents
```

## 2. Standardized Request & Response Envelope

All API endpoints should conform to the standard envelope defined in `src/types/api.ts`:

```typescript
export interface ApiResponse<T> {
  data: T;
  success: boolean;
  message?: string;
  timestamp: string; // ISO 8601
}

export interface ApiError {
  message: string;
  statusCode: number;
  code?: string;
  details?: Record<string, any>;
}
```

Authentication is handled via Bearer tokens passed in the standard header:
`Authorization: Bearer <jwt_or_api_token>`

## 3. Proposed REST API Endpoints

### 🎯 3.1 Goals (`src/api/services/goalService.ts`)

| Method | Endpoint | Description | Request Body | Response Payload |
|---|---|---|---|---|
| `GET` | `/goals` | List all goals for authenticated user | None | `Goal[]` |
| `GET` | `/goals/:id` | Get details, constraints & status of a goal | None | `Goal` |
| `POST` | `/goals` | Initialize new real-world goal | `CreateGoalRequest` | `Goal` |
| `PATCH` | `/goals/:id` | Update goal status or constraints | `Partial<Goal>` | `Goal` |
| `DELETE`| `/goals/:id` | Archive or delete goal | None | `{ success: boolean }` |

### ✅ 3.2 Tasks (`src/api/services/taskService.ts`)

| Method | Endpoint | Description | Request Body | Response Payload |
|---|---|---|---|---|
| `GET` | `/tasks?goalId=:id` | Get actionable task checklist | None | `Task[]` |
| `POST` | `/tasks` | Create task attached to goal | `CreateTaskRequest` | `Task` |
| `PATCH` | `/tasks/:id` | Toggle completion status | `{ isCompleted: boolean }` | `Task` |
| `DELETE`| `/tasks/:id` | Remove task | None | `{ success: boolean }` |

### 📄 3.3 Documents & OCR (`src/api/services/documentService.ts`)

| Method | Endpoint | Description | Request Body | Response Payload |
|---|---|---|---|---|
| `GET` | `/documents?goalId=:id` | List verified & missing documents | None | `DocumentItem[]` |
| `POST` | `/documents/upload` | Upload PDF / scan for Document Agent OCR | `multipart/form-data` | `DocumentItem` |
| `DELETE`| `/documents/:id` | Remove document | None | `{ success: boolean }` |

*Note for OCR pipeline*: When a document is uploaded, Document Agent parses validity dates, issuing authority (e.g. Tehsildar, UIDAI), and seals. Verification state changes from `reviewing` to `verified`.

### 🧭 3.4 Plan Synthesis & Governance (`src/api/services/planService.ts`)

| Method | Endpoint | Description | Request Body | Response Payload |
|---|---|---|---|---|
| `GET` | `/goals/:goalId/plan` | Fetch multi-phase plan generated by Planning Agent | None | `GoalPlan` |
| `POST` | `/plans/:id/decision` | User decision (Approve, Modify, Reject) | `PlanDecisionRequest` | `GoalPlan` |

*Zero Silent Execution Guarantee*: An approved plan allows the Action Agent to stage external actions. A modified plan triggers re-verification.

### ⚡ 3.5 Action Center Approvals (`src/api/services/actionService.ts`)

| Method | Endpoint | Description | Request Body | Response Payload |
|---|---|---|---|---|
| `GET` | `/actions` | Get pending actions requiring signature | None | `ActionItem[]` |
| `POST` | `/actions/:id/decision` | User authorizes or rejects consequential action | `ActionDecisionRequest` | `ActionItem` |

### 🤖 3.6 Agents & Operations Center (`src/api/services/agentService.ts`)

| Method | Endpoint | Description | Response Payload |
|---|---|---|---|
| `GET` | `/agents` | Get health & status of the 7 agent fleet | `AgentInfo[]` |
| `GET` | `/agents/:id` | Get reasoning trace & last outputs | `AgentInfo` |

### 🔍 3.7 Research, Maps & Verification

* `GET /research/search?q=:query` — Scans PG listings, rent databases, student reviews.
* `GET /maps/commute?origin=:from&dest=:to` — Returns verified transit matrix, Red Line metro timetable, walking distance.
* `GET /verification/audit?goalId=:id` — Returns mathematical proofs (`Rent + Food + Transit ≤ Budget`).

## 4. Real-Time WebSocket Specification (`src/services/websocket.ts`)

**Endpoint**: `ws://<host>/ws/agents`  
**Authentication**: Passed as query parameter `?token=<jwt>` or initial auth handshake message.

### Event Format:

```json
{
  "type": "agent:progress",
  "agentId": "agent-research",
  "agentType": "research",
  "goalId": "goal-lucknow-college",
  "timestamp": "2026-08-10T14:32:00Z",
  "payload": {
    "actionDescription": "Research Agent found 3 PG options in Indira Nagar within ₹10,000/mo",
    "progressPercentage": 60,
    "resultSummary": "3 accommodations verified"
  }
}
```

### Supported Event Types:

1. `agent:started` — Agent begins task execution.
2. `agent:progress` — Incremental updates (streamed to home ticker & activity feed).
3. `agent:completed` — Execution finished with verified result.
4. `agent:failed` — Agent encountered error or missing constraint.
5. `research:result` — New listings or web facts indexed.
6. `maps:commute_verified` — Transit timetable validated.
7. `verification:audit_complete` — Mathematical proofs validated.
8. `plan:generated` — Planning Agent synthesized new plan.
9. `action:requested` — Consequential action staged awaiting user authorization.
10. `action:executed` — Action confirmed and processed.

## 5. Frontend Error & Retry Handling

* **Network Disconnects**: `ApiClient` catches status 0 network errors and notifies the user via friendly toast without crashing.
* **WebSocket Reconnect**: `AgentWebSocketService` implements automatic exponential backoff reconnection when disconnected.
* **Fallback**: When in `mock` mode, the app runs completely standalone without requiring backend services to be running.
